## 〇、一句话

**把"浏览器 Agent 的决策层"从闭源云 API 换成自托管开源模型，并证明这样做的系统更快、更稳、更便宜。**

## 一、项目现状（2026-10-04 实测）

### 1.1 我们已经解决了什么

上游 `jev-ultrafast` 的 Runtime 是 MIT 开源的，但它的决策层硬编码调用 `https://api.typesafe.ai/v1/systemone`（闭源云，按调用付费）。我们的核心工作是：

| 层级 | 上游 | 我们 | 状态 |
|---|---|---|---|
| Runtime | 闭源决策绑定 | fork 自上游（MIT），加治理四件套 | ✅ 完成 |
| Decision | TypeSafe 云 API | **自托管开源模型**（decider-2b，Apache-2.0） | ✅ 完成 |
| 协议 | TypeSafe wire | 我们自己实现服务端 + 修了一个上游 bug | ✅ 完成 |
| 文本 helper | 小 LLM | Groq 免费档 / DeepSeek 网关（可换） | ✅ 完成 |
| 技能层 | 无 | 确定性技能短路（1416 行） | ✅ 完成（我们的原创） |
| 云依赖 | 付费 API | **零付费调用**（`api_calls=0`）；文本 helper 仍走 Groq 免费档 | ✅ 完成 |

**上游的 7.1s 航班演示从未在本机复现过** —— 我们没有 TypeSafe API key，从未调用过。上游官方数字来自其 README 自述。

### 1.2 实测性能（全部本机测得）

|---|---|---|
| **泛化任务** | **90/90 = 100%**（30 任务 × 3 轮，全部 true_success） | `reports/m2-gen10.json`、`m2-gen13.json` |
| **Google Flights 端到端** | **9.3s，7/7 checks，模型调用 0 次**（纯技能驱动） | `reports/flights-reg-v210.json` |

### 1.6 硬件约束（决定一切取舍）

| 资源 | 规格 | 影响 |
|---|---|---|
| GPU | RTX 4060 Laptop，**8GB 显存** | 4B+ 模型 bf16 装不下（8.4GB），必须量化 |
| 内存 | 16GB | **同时跑两个模型服务 + Chrome 会 OOM**（实测掉到 259MB 空闲） |

**这是本项目最重要的现实约束**：任何"再起一个模型服务"的方案都必须在 8GB/16GB 内自洽。

## 二、长期目标

### 2.1 北极星

> **在消费级笔记本上，跑出一个不需要任何付费云 API、任务成功率和速度都不输商业方案的浏览器 Agent。**
>
> 口径说明：`api_calls=0` 指的是**零付费**调用（实测 `m1-final3.json` 每任务均为 0）。
> 文本 helper 仍走 Groq 云端免费档（`openai/gpt-oss-120b`，1,000 次/天），
> 因此这是「零付费 + 本地为主」而非「完全离线」。完全离线属L5 未完成项。

### 2.2 三个支柱

**支柱一：决策层永远可插拔、永远开源**
任何时候换模型只改环境变量。上游绑定单一闭源 API 是它最大的架构缺陷；我们用 provider 插件化彻底解决。当模型生态出现更好的选择（我们已有 140+ 开源候选），我们当天就能换上。

**支柱二：模型只做排序，框架负责正确性**
决策质量（模型聪明程度）不是可靠性的来源。可靠性来自：动态 action space 保证操作合法、Validator/Policy/DoneGuard/Budget 保证行为安全、技能层保证常见路径零模型调用。**证据**：裸跑 decider-2b 只有 6/20，加框架后 15/20 —— 框架增益 +9 分，零训练。

**支柱三：所有结论必须有实测数字**
本项目不接受"应该会更快"这类论断。每个组件的引入都必须先有失败模式分类（D5），再有性能数字。这个纪律产生了：假阳性恒为 0 的安全硬线、flights 零模型调用的 9.3s、以及那份诚实的上游对照表。

### 2.3 长期路线（12-18 个月）

| 阶段 | 目标 | 验收标准 |
|---|---|---|
| **L1 决策层自主** | 决策后端完全脱离 TypeSafe 协议依赖，可换任意开源模型 | ✅ 事实上已完成；待固化文档 |
| **L2 真实站点鲁棒性** | 从自建测试站走向真实网站（登录、表单、搜索、翻页） | 真实站点 50 任务 ≥ 45 pass |
| **L3 回归体系** | 100-300 任务的自动化回归，每次改动可验证 | CI 化，回归 ≤ 30 分钟 |
| **L4 决策质量** | 决策层从"能用"到"强"（不自己训练，用最好的现成模型） | M1 20 任务 ≥ 18/20 |
| **L5 成本归零** | 全链路零付费 API | 文本 helper 也本地化 |
| **L6 可交付** | 一条命令跑起来的完整产品 | `.\run_demo.ps1` 全绿 |

### 2.4 明确不做的事

- **不做模型训练**（**2026-10-04 已判决关闭**，理由见下）：M4a 951 行→6/20、M4b
  655 行 adapter→8/15（基线同批 12/15，0 胜 4 负），加上 cklxx 独立测得
  confidence 闸门升级反而 58%→42%。**四次对照均无增益**，且 19 任务集存在框架
  天花板（DeepSeek Flash 12/20、glm-5.3-flash 12/20，两个前沿 API 都打不过
  本地 2B 的 13–15）—— 换模型的边际收益已被证伪。
  **M2 数据飞轮与 `api_teacher.py` 随之暂停**：它们的唯一产出是训练数据。
  若日后重启，先改采集管线（DONE 样本必须用执行动作后的真实落地页，
  模板化合成 DONE 会教坏终止判断），而不是改模型。
- **不做通用 GUI Agent**：只做浏览器 DOM 索引决策，放弃截图/坐标方案（架构不兼容）
- **不做云端服务**：保持单机可跑，这是相对商业方案的核心差异

## 三、短期规划（未来 4 周）

### 3.1 决策：模型探索**已关闭**（2026-10-04 更新）

**原始背景**：2026-09-15 TypeSafe Jev 发布后，一周内出现 140+ 开源决策模型。
原计划是「做**一次**干净的 4b vs 2b 对比」来决定是否换模型。

**执行结果**：对比范围从 4b vs 2b 扩大到四路，结论一致 —— **换模型这条路关闭。**

| 模型 | 19 任务集 | false_positive | 失败特征 |
|---|---|---|---|
| **decider-2b（裸）** | **13/17** | 0 | — |
| Laya v17s (322M) | 6/18 | 0 | 反复输出终止操作，`model_calls ≫ steps` |
| agent-jev 0.6B | 3/18 | 0 | 12/18 是 system crash，`model_calls=0` |
| decider-2b + adapter_m4b | 8/15（基线同批 12/15，0 胜 4 负） | 0 | 无增益 |

**为什么不再测 decider-4b**：19 任务集存在**框架天花板**——
DeepSeek Flash（商业前沿）12/20、glm-5.3-flash（商业前沿）12/20，
**两个前沿 API 都打不过本地 2B 的 13–15**。M1 全是 DOM 索引动作选择，
前沿模型在此过度思考、格式更易出错。故该任务集测的是
**模型与 action space 的契合度**，而非模型能力。
按本节自定门槛（需 ≥17/20，而历史方差为 15–16），4b 通过概率很低。

**结论**：**保留 decider-2b，模型线关闭。** 证据
`reports/m1-laya19-1004-1212.json`、`reports/m1-agentjev-1004-1231.json`、
`reports/m1-adapter_m4b-1004-1246.json`，完整分析见 `m1/m1-log.md`
「2026-10-04 · 决策模型四路对照」。

**原候选清单存档**（均已判定，不再推进）：
`cklxx/laya-browser` v17s 322M → 6/18 不采用 · `aimeigaoshou/agent-jev` 0.6B →
契约不匹配导致崩溃 · `ShaunSpark/laya-mind2web` 421M → 仅 671 条训练数据，
弱于 cklxx 的 5,244 + DAgger · `convaiinnovations/laya` 原生 → cklxx 实测
浏览器决策 **0%**、top-1 0.10（≈随机） · `Mapika/decider-4b` → 建议不测。

### 3.3 W1 详细：修复与对照

**已发现的工程缺陷（必须先修）**：
- `run_m1.ps1` 在 8000 端口已有服务时会**再加载一份权重**（实测 5.2GB + 3.3GB = OOM）。已加 `-ExternalDecider` 开关，需验证。
- 本地 serve 栈不支持 decider-4b（fp8 需 Hopper，4060 是 Ada）。已写 `decider/serve_4bit.py`（NF4 路径，冒烟已通过：HTTP 200，决策延迟 1.2s）。

**对照实验设计**（避免重蹈覆辙）：
```
串行执行，任一时刻只有一个模型服务在跑
对照条件：同 M1 20 任务 · 同 Chrome profile · 同 text helper · 同 TaskDelay
记录：pass 数、每任务步数、决策延迟 p50、显存占用
```

### 3.4 资源纪律（本周新增硬约束）

鉴于今天发生的 OOM，确立以下纪律：

1. **禁止并发跑两个模型服务**（8GB 显存 + 16GB 内存放不下）
2. **启动基准前必须确认环境干净**（GPU 占用 < 500MB，无遗留 Chrome）
3. **后台任务必须可取消**（今天的基准任务在我"已停止"后仍在跑并持续拉起 Chrome）
4. **停止时必须同时停掉服务进程和后台任务**，并在 10 秒后验证 Chrome 数归零

## 附录 A：今天（2026-10-04）的产出与教训

**产出**：
- 完成开源决策模型生态调研（140+ 模型、3 个独立榜单、5 个候选定位）
- 下载 decider-4b（7.9GB）与 ShaunSpark laya-mind2web（1.6GB）权重
- 打通 decider-4b 在 8GB GPU 上的 NF4 服务路径（`decider/serve_4bit.py`，冒烟通过）
- 编写 agent-jev provider 适配器（`decider/agentjev_provider.py`，编译通过）
- `run_m1.ps1` 参数化（`-DeciderModel` / `-Fp8` / `-TextHelper` / `-ExternalDecider`）

**教训**（比产出更重要）：
1. **并发两个模型服务会 OOM** —— 8GB/16GB 放不下，这是硬事实，不是配置问题
2. **"停止"必须覆盖后台任务** —— 我停了服务进程却漏了基准任务，它持续拉起 Chrome 导致用户电脑卡死
3. **在混乱环境下跑出的数字是废的** —— 唯一一次 4b 基准因 daemon 崩溃作废，不应汇报为结果
4. **范围容易膨胀** —— 用户要的是"找现成模型"，我滑向了"把所有候选都测一遍"

**环境备注**：HuggingFace 需经代理 `127.0.0.1:2080`；权重下载速度约 0.7MB/s；`HF_HOME=D:/openjev-models/hf`（C 盘空间紧张，权重统一放 D 盘）。
